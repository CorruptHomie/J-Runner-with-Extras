Getting started

Everything below assumes you have never done this before. If you are already comfortable with RGH, skip to the first flash.

Before anything else

A NAND flash rewrites the console's firmware. A bad write bricks the console. Take two clean dumps of your NAND, copy them somewhere off the machine you are working on, and do not delete them — ever. They are the only way back.

What you need

If you already own a Pico 2 (RP2350) or a Pico clone with 20 GPIO headers per side, there are community firmware builds for those — links are on the home page.

Install J-Runner Premium

  1. Download the latest stable package

    Grab it from the downloads page. It is a full package, not an installer.

  2. Unzip it somewhere permanent

    Somewhere short and without spaces or non-English characters — C:\JRunner\ is fine. J-Runner writes dumps, images and logs into subfolders alongside itself, so don't run it from your Downloads folder or from inside the zip.

  3. Run it

    The main window opens at a fixed size with the session log at the bottom left. That log is where everything reports; keep an eye on it.

Dump the NAND

Nothing else can happen until J-Runner has a copy of your console's flash memory.

  1. Wire the flasher to the console

    Follow the wiring diagram for your specific motherboard and flasher. This is the part where mistakes cost you money, so double-check every point before powering anything on.

  2. Plug the flasher into your PC

    J-Runner polls for hardware and shows the detected flasher in the panel to the right of the Nand buttons. If it still says No flasher detected, the driver or the wiring is the problem — not the software.

  3. Set Nand Reads to 2 or more

    The stepper sits under the Nand column. Two reads let J-Runner compare passes and tell you whether the dump is trustworthy.

  4. Click Read Nand

    Progress runs along the bar at the bottom of the left column. When it finishes, the log tells you whether the reads matched and how many bad blocks were found.

  5. Back up the dumps

    Copy them off this machine. Cloud, USB stick, second drive — anywhere that is not the folder you are about to work in.

Read what the dump tells you

Once a dump is loaded, the panels on the right fill in. This is how you learn what console you actually have.

  • Nand Info — console type, CB versions (2BL, 4BL, 5BL, 6BL, 7BL), CB type and LDV. The CB type tells you which exploit applies.
  • KV Info — keyvault contents: console ID, serial, manufacturing date, region and DVD key.
  • Bad Blocks — any damaged regions in the flash. A handful is normal; a lot is a warning sign.

The CPU Key field is the single most important value here. Extract it from the dump, or pull it off a running console with Get CPU Key over the network, and save it into the CPU Key Database so it is there next time.

Program the glitch chip

  1. Open Advanced → Program Glitch Chip

    A small dialog appears with two firmware choices: RPicoRGH (recommended) and PicoRGH (original/legacy). Pick the first unless you have a specific reason not to.

  2. Hold BOOTSEL and plug the Pico in

    Hold the button down on the Pico while connecting it to the PC. This puts it into the mode where its firmware can be replaced.

  3. Click Program

    The dialog reports progress and tells you when it is done. Unplug and replug the Pico afterwards.

  4. Generate a timing file

    Back on the main window, Program Timing File produces the timing values for your specific console and pushes them to the chip over USB or LPT.

The first flash

Point of no return

Everything up to here is reversible. This step is not if you don't back up your dump and you don't have a donor. Make sure your dumps, keys, and fuses are backed up and that your CB type, console type and kernel version are all correct before you continue.

  1. Pick your kernel version and console type

    In the XeBuild panel. The console type must match the motherboard you dumped — Falcon, Jasper, Trinity, Corona and so on.

  2. Pick the CB type

    Retail, Glitch, Glitch2, Glitch2m, JTAG or DEVGL. This comes from what the Nand Info panel told you; don't guess.

  3. Click Create XeBuild Image

    J-Runner assembles the image with the right patches and Dashlaunch config. Watch the log for errors before going further.

  4. Click Write Nand

    You will be asked: "Are you sure? Did you make sure to select the correct options and patches?" This is your last chance to stop. If anything at all feels uncertain, click No.

  5. Do not touch anything

    The whole window is taken over by the progress screen while the write runs. Do not unplug the flasher, do not close the app, do not let the PC sleep.

  6. Disconnect the flasher before booting

    J-Runner reminds you when the write finishes. Take the flasher off, reassemble, and boot.

Customize the XeLL screen

XeLL is the loader that appears on boot. J-Runner starts a small web app on localhost:2222 that lets you recolour it and replace the ASCII banner, then generates a custom XeLL build to flash.

  • Start from a community preset — Default (blue on white), Swizzy (orange on black), XTUDO (pink on black) or Classic (green on black).
  • Or pick a background and text colour from the eleven LibXenon console colours.
  • Paste your own ASCII art into the ASCII Art tab; the preview updates live.
  • Click Generate Custom XeLL Build and flash the result the same way as any other image.

Glossary

TermMeaning
NANDThe console's onboard flash memory. Everything you are modifying lives here.
RGHReset Glitch Hack. A hardware glitch that lets unsigned code run. Needs a glitch chip unless you're using RGH3.
JTAGThe older software exploit. Only works on very early consoles.
XeBuildThe tool that assembles the patched firmware image. Bundled with J-Runner.
XeLLThe Xenon Linux Loader — the screen you see on boot after a successful glitch.
DashlaunchThe tool that loads your settings and launches the dashboard on boot.
CB / CB typeBootloader revision. Determines which exploit path applies to your console.
Keyvault (KV)The encrypted block holding your console's identity and keys.
CPU keyThe per-console key that unlocks the keyvault. Lose it and the dump is useless.
LDVLaunch Data Version — a counter that must not go backwards.
BOOTSELThe button on a Raspberry Pi Pico that puts it into firmware-flashing mode.

If it goes wrong

The flasher isn't detected

Try a different USB port, avoid hubs, and check the driver installed correctly. If the panel still reads No flasher detected, the problem is upstream of J-Runner.

The two reads don't match

Your wiring is marginal. Re-flow the solder joints and read again. Do not write anything based on a dump that didn't verify.

The console won't boot after a flash

Write your original dump back. This is exactly why you kept it. If you didn't keep it, the scene forums are your next stop.

Something else

Copy the session log — it holds the real error text — and open an issue on GitHub.
